### Android: rules on basic-info dates are not shown

R3 is the only matrix rule that validates a "basic info" date (the event date), so its message has
no data element or attribute to attach to. Two diagnostic rules confirmed the pattern on Android:

| Rule                                            | Case                | Android                                                        |
| ----------------------------------------------- | ------------------- | -------------------------------------------------------------- |
| R8 enrollment date on or before current date    | enrollment tomorrow | silent, enrollment saved                                       |
| R9 visit date after 2000-01-01                  | visit 2000-01-02    | silent (correct)                                               |
| R9                                              | visit 2000-01-01    | inconclusive: the facility opens 2000-01-01, so the form locks |
| R3 after metadata re-sync, re-opening the event | visit 09-29         | still silent, save and complete allowed                        |

When the device synced the R3 event, **DHIS2 rejected it** ("Generated by ProgramRule … Must be
on or after Enrollment date"), so the record stays on the device with a sync error. This is the
open Android feature gap [ANDROAPP-7843](https://dhis2.atlassian.net/browse/ANDROAPP-7843)
("Android support program rule actions on basic info fields"). The tool cannot attach such a
message to a field, so it now warns when a rule on an enrollment, incident, event or due date is
created, and the README / manual list the limitation.

### Blocking behaviour differs between clients

- **Capture web:** the test stage uses the DHIS2 default validation strategy `ON_COMPLETE`, so an
  error blocks **completing** the event but not a plain save. The registration form (R6) blocks
  saving outright. Errors are shown inline at the field; R3's (no field) in the form's Error box.
- **Android:** an error blocks **saving** ("Not saved – Some fields have errors"); warnings
  are listed in the save dialog but don't block. The section badge counts every error twice
  (cosmetic, Android).

## 4. Server-side enforcement (observation, not an app issue)

Tracker imports of the matrix cases through `/api/tracker` only triggered the enrollment-level
rule (R6) on 2.42.6. Stage-scoped event rules did not fire on import, neither nested in an
enrollment nor as a separate event import, while the Android sync above shows the server
enforcing R3. The cause of the difference was not determined. The rules behave correctly in both
client apps, which is where data entry is blocked.
